Happy-path purchase flow

  • 1Client sends POST /purchase → Caddy → ticket-purchase
  • 2ticket-purchase checks seat availability with event-catalog (reserves atomically in Postgres)
  • 3ticket-purchase calls payment to charge the card (retries up to 3×)
  • 4On success, pushes jobs to fraud:queue, analytics:purchase:queue, and notification:pubsub in Redis
  • 5fraud-worker consumes fraud:queue, validates the order, auto-refunds if flagged → fraud:dlq
  • 6analytics consumes purchase/browse/refund queues and records to analytics-db
  • 7notification subscribes to the pubsub channel and dispatches confirmations

Waitlist & edge cases

  • 1If event-catalog returns 409 (no seats), ticket-purchase pushes a job to waitlist-jobs-{eventId}
  • 2waitlist-worker retries the purchase when seats free up, calling ticket-purchase and payment directly
  • 3Refunds go through the refund service → updates Postgres, pushes to analytics:refund:queue, calls event-catalog to unreserve seats
  • 4All /events reads are cached in Redis (60s TTL). Cache is busted on seat reservation or seeding
  • 5Idempotency keys (purchase-idem:{key}) prevent duplicate charges if the client retries

Service reference

⚡

Caddy

:3000 (public)

Reverse proxy and load balancer. Routes /purchase, /payment, /events, /dashboard to the correct upstream using round-robin with DNS-based service discovery.

Gateway
🎫

ticket-purchase

:3000 (internal)

Orchestrates the full purchase flow. Checks seat availability, charges via payment, pushes to fraud/analytics/notification queues, and manages idempotency keys in Redis.

Service
💳

payment

:3001 (internal)

Processes card charges. Validates card type (Visa / Master / Amex), stores payment records in payment-db. Returns a paymentID used for fraud tracking and refunds.

Service
📋

event-catalog

:3005 (internal)

Manages event listings and seat inventory. Caches responses in Redis (60s TTL). Seat reservation uses a Postgres row-level lock (FOR UPDATE) to prevent overselling.

Service
↩️

refund

:3000 (internal)

Handles refund requests from fraud-worker or clients. Unreserves seats in event-catalog, updates the DB, and pushes a refund event to the analytics queue.

Service
👤

users

:3006

User account management. Stores user profiles in users-db. User IDs are passed as x-user-id headers so analytics can attribute browses and purchases.

Service
🔍

fraud-worker

:3000 (internal)

Consumes fraud:queue. Flags orders with >6 seats, price >$500, or >4 attempts from the same card. Flagged orders are auto-refunded; unprocessable ones go to fraud:dlq.

Worker
📊

analytics

:3000 (internal)

Consumes purchase, browse, and refund queues from Redis. Records aggregated event data to analytics-db. Failed messages go to analytics:dlq.

Worker
🔔

notification

:3000 (internal)

Subscribes to notification:pubsub in Redis. Dispatches purchase confirmation messages. Pub/sub means all replicas receive every notification.

Worker
⏳

waitlist

:3000 (internal)

Consumes waitlist-jobs-{eventId} queues. When seats free up (via unreserve), retries the purchase by calling ticket-purchase or payment directly.

Worker
🔴

Redis

:6379 (internal)

Central message broker and cache. Hosts all queues (lists), DLQs, idempotency keys (hashes), event cache (strings), and notification channels (pub/sub).

Broker Cache
📡

dashboard

:3007

Monitoring UI. Polls all service health endpoints, reads queue depths from Redis, streams Docker container CPU/network stats via the Docker socket, and runs k6 load tests.
